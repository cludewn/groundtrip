## 1. ねらい

**審査員に伝える一言**

> AIの旅程は、もっともらしいけれど、根拠が見えず、現地で崩れます。GroundTripは、AIの提案を、根拠と一緒に見せて、直すのは1地点だけ、決めるのは本人、という流れにしました。

見せたいこと（優先順）：

1. AIが作った旅程は**提案**であり、確認済みの事実ではないこと（**未照合**と明示される）。
2. 根拠は「情報源と整合／矛盾あり／確認できない」に分かれ、「整合」は現実の正しさの保証ではないこと。
3. 直すのは**選んだ1地点だけ**で、固定予定と、承認前の旅程は変わらないこと。
4. 学びは**本人が承認したものだけ**で、AIの再学習ではないこと。

### 5分版（オンライン用）に伸ばす場合の差分

4分版に、次の約1分を足します。

- 導入に +15秒：課題を、旅行中に崩れる具体例（閉店・遅れ）で話す。

## 2. 事前準備

### 2.1 環境

1. Node.js 24.15以上の24系と、pnpm（`package.json` の `packageManager`）を用意し、`pnpm install --frozen-lockfile` を実行する。
2. `.env.example` を `.env.local` にコピーし、次を設定する（値はコミットしない）。

   | 変数                          | 設定                             | 用途                                   |
   | ----------------------------- | -------------------------------- | -------------------------------------- |
   | `GOOGLE_CLOUD_PROJECT`        | 使うGoogle CloudプロジェクトのID | Vertex AI（Gemini）                    |
   | `GOOGLE_CLOUD_LOCATION`       | 省略時は `global`                | 同上                                   |
   | `GEMINI_MODEL`                | 省略時は `gemini-3.5-flash`      | 同上                                   |
   | `TRIP_GENERATION_ENABLED`     | `true`                           | 旅程の生成API。既定は無効（503）       |
   | `LEARNING_CANDIDATES_ENABLED` | `true`                           | 学びの候補の作成API。既定は無効（503） |
   | `TRIP_VERIFICATION_ENABLED`   | `true`（**要・PR #27**）         | 旅程の照合API                          |
   | `TRIP_REVISION_ENABLED`       | `true`（**要・PR #28**）         | 部分修正の候補API                      |

3. Geminiの認証はADC（Application Default Credentials）。ローカルでは `gcloud auth application-default login` でログインする。Places・Routesを使う場合（要・PR #27・#28）も、同じADCを使う。**APIキー・トークンは、台本にも画面にも出さない。**
4. `pnpm dev` を起動し、ブラウザで `http://localhost:3000` を開く。
5. Firebase Emulator（`pnpm emulators`。Java 21以上が必要）は、**このデモの主な手順では不要**です。`main` の旅程生成・学びの候補の作成は、認証を要求しません。Emulatorが要るのは、`GET /api/auth/session` と、永続化（要・PR #44）を見せるときだけです。

### 2.2 サンプルデータとアカウント

- **使うアカウント**：`main` の画面は、ログインを要求しません。デモ用に新しく作る必要はありません。永続化（要・PR #44）を見せる場合だけ、Firebaseの匿名認証を使います（匿名認証は、身元の保証ではありません）。
- **架空のサンプル**：`/demo`（路線図）と `/reflection`（振り返り）は、`src/domain/samples.ts` の架空の旅程（「京都市・東山（架空デモ）」、朝の庭園・昼食店A・14時の予約展示）を使う。施設・営業時間・移動時間は、実在の情報ではない。
- **生成の入力例**（実際にGeminiを呼ぶ手順1用）：旅行先「京都・東山」、日付は将来の日付、希望「ゆっくり街歩きしたい」、固定予定1件（名前「予約済みの展示（任意）」、開始 14:00、滞在 60分）。生成される地点は、**毎回変わる**。

### 導入（0:00〜0:25）（社会課題）

- **操作**：トップ画面（`/`）を開いておく。
- **話すこと**：「AIに旅程を作らせると、もっともらしいのに、施設が閉まっていたり、移動が間に合わなかったりします。旅行中に崩れても、AIの提案をそのまま信じるしかありません。GroundTripは、AIの提案を、人間が根拠で選ぶためのアプリです。提案、照合、制約チェック、本人の承認を、混ぜずに分けています。」

### 手順1：旅程を作る [main]（0:25〜1:10）（技術活用）

- **操作**：トップ画面で、旅行先・日付・希望を入力し、**固定予定を1件**（14:00、60分）追加して、「旅程を作成する」を押す。
- **見えるもの**：
  - 生成中の表示のあと、縦型の路線図に、3〜4地点の旅程が出る。
  - 固定予定は、入力どおりの名前・時刻・滞在で表示され、ロックの表示が付く。
  - 生成された地点の根拠は、「確認できない」ではなく**未照合**として表示される（照合はまだ行っていない）。
  - 路線図の下に、「路線図は旅の順番を表すもので、実際の地図ではありません」と表示される。
- **操作（続き）**：予定を1つ選び、詳細シートを開く。「この予定を固定する」と「固定を解除する」を見せる。
- **話すこと**：「Gemini（Vertex AI）が作ったのは**提案**です。出力は、スキーマで検証してから使っています。施設の実在や営業は、まだ確認していません。だから**未照合**と出ます。入力した固定予定は、AIが書き換えても、入力どおりに戻しています。」
- **注意**：画面上の固定の切り替えは、まだ保存されません（画面に「画面上の変更で、まだ保存されていません」と出る）。**生成に失敗すると、以前の旅程は表示から消える**（入力内容だけが残る）ので、成功したあとは、再生成しない。
- **代替の流れ（生成が失敗したとき）**：5節のフォールバックを参照。

### 手順2：根拠の照合（1:10〜1:45）（技術活用）

`main` では、Places・Routesを呼ぶAPIがなく、**生成した旅程の画面に、照合結果は出ません。** 照合の実装（`POST /api/trips/verify`）は PR #27 で、画面への接続は、さらに別の作業です。

**A. 実際に照合する版（要・#27のマージと画面接続）**

- 生成した旅程の画面に、照合結果が出る状態になっている場合だけ行う。Places（施設の同定・営業時間）とRoutes（徒歩の移動時間）の根拠が、予定ごとに、「情報源と整合」「矛盾あり」「確認できない」で出る。**課金されます。**
- 画面接続がない場合、`POST /api/trips/verify` をAPIとして呼ぶ見せ方はありうるが、「完成した画面の機能」としては紹介しない。
- **間に合わなかった場合の代替**：下のBに切り替え、「実際の照合の画面接続は、まだです」と、はっきり言う。

**B. `main` で実演できる版 [デモ用の想定]**

- **操作**：`/demo` を開く。「モックデータ（架空）」の注記が出ていることを見せる。予定を選び、詳細シートの根拠を見せる。
- **見えるもの**：朝の庭園は「情報源と整合」（出典は「架空デモ」）、昼食店Aは「矛盾あり」、14時の予約展示は「確認できない」。出典・照合日時・対象日時の欄がある。
- **話すこと**：「これは**デモ用の想定**で、実際のAPIの結果ではありません。根拠は、情報源と整合、矛盾あり、確認できない、の3つに分けます。**整合は、現実の正しさの保証ではありません。**取得した時点の情報源と合っていた、という意味です。Places・Routesのアダプターは実装済みですが、画面への接続は、まだです。」

### 手順3：1地点の部分修正（1:45〜2:40）（完成度）（要・PR #38）

- **操作（PR #38のマージ後の `/demo`）**：昼食店Aの詳細シートで「この予定だけ変更」を押し、理由を入れて候補を出す。候補を切り替えて、路線図の分岐（選んだ候補は青、元の経路はグレー）と、変更前後の差分を見せる。固定予定（朝の庭園・14時の予約展示）は、「この予定だけ変更」が押せないことを見せる。
- **見えるもの**：最大3候補の比較。候補ごとに、変更前後の予定、隣の移動区間、根拠、制約判定、本人の承認の状態が、別々に出る。**承認するまで、元の旅程は変わらない。**
- **話すこと**：「直すのは、選んだ1地点だけです。固定予定は、変更の対象にできません。候補を選ぶことと、正式に承認することは、別の操作です。」
- **[デモ用の想定]**：PR #38の `/demo` の候補は、画面側に用意した**模擬の候補と模擬の経路**で、実際のGeminiやPlaces・Routesの結果ではありません（そう話す）。
- **実際の候補（要・PR #28のマージ、`TRIP_REVISION_ENABLED=true`）**：トップ画面で生成した旅程から、同じ操作で、`POST /api/trips/revise` が候補を作る。課金されます。
- **未接続（話すときの線引き）**：承認した修正を、サーバーで適用して保存する処理は、PR #38・#44の時点で未接続です。承認後の画面の動きは、マージ後に実機で確かめてから、台本を書き直す。
- **マージされなかった場合の代替**：この手順は「見せられない」。`main` の路線図で、詳細シートと固定の切り替え（固定予定は保たれる）を見せ、部分修正は**設計の説明にとどめる**。その時間は、手順1・6に回す。

- 「できる」とは言わない。つながっていない部分を、動いているように見せない。

### 手順6：振り返りと学びの承認 [main]（3:10〜3:45）（完成度）

- **操作**：`/reflection` を開く（「確認用のページです。旅程はサンプル（架空）」の注記が出る）。感想を入力し（例：「昼食のあとに休みたかった」）、「学びの候補を作る」を押す。候補を1件編集し、承認し、別の1件を却下する。
- **見えるもの**：候補は、すべて**未承認**で出る。「情報源との不一致」と「個人の好み・経験」の区別が出る。承認済みの学びが、別の欄に並ぶ。承認済みの内容を編集すると、未承認に戻る。
- **話すこと**：「学びの候補は、Geminiが作ります。次の旅行に使うのは、**本人が編集し、承認したものだけ**です。AIが学習し直すわけではありません。」
- **正直に言うこと**：画面に「いまの画面で承認しても、承認した内容は保存されず、次回の旅程づくりにも反映されません」と出ている。**`main` では、保存先が未接続です。** 保存の実装（Firestore、利用者ごとの認可）は PR #44（レビュー中）です。
- **[デモ用の想定]**：旅程はサンプル（架空）。デモ用の模擬の報告は、実際の出来事として学びにしない（アプリ側で除外している）。
- **マージされなかった場合の代替**：PR #44は不要。`main` のまま、「承認までを見せ、保存は今後」と説明する。

### 手順7：次の旅行への反映と、まとめ（3:45〜4:00）（ピッチ）：反映は接続できた場合のみ

- 承認した学びを次の旅程の生成に反映する画面は、**ありません**（旅程の作成フォームは、学びを常に空で送る）。**接続できた場合のみ見せます。** 接続できなかった場合は、見せず、**設計の説明にとどめる**：「生成の入力には、承認済みの学びを渡せるデータの形を用意してあります。画面からの利用は、これからです。」
- **まとめの一言**：「AIの提案を、人間が根拠で選ぶ。提案・照合・制約チェック・承認を分けて、固定予定を守り、学びは本人が承認したものだけ。」と言う。使っているGoogle技術（Gemini、Places、Routes、Firebase）を挙げるのは、**提出時に実際に接続できたものだけ**にする。

## 6. 想定される質問と答え

### なぜ、AIの提案をそのまま使わないのですか。

AIの旅程は、もっともらしい一方で、施設の実在・営業時間・移動時間の正しさを保証しません。GroundTripは、Geminiの文章を正しさの証拠にしません。提案、照合、制約チェック、本人の承認を分け、最後は本人が根拠を見て選びます。AIのミス探しを利用者に強いるのではなく、旅程の一部を直す操作の中で、根拠を確認できるようにしています。

### 「情報源と整合」とは何ですか。正しいということですか。

いいえ。**取得した時点の情報源と、矛盾しなかった**という意味です。現実の正しさ、将来の営業、当日の混雑は保証しません。根拠は、「情報源と整合」「矛盾あり」「確認できない」の3つに分け、出典・照合日時・対象日時を示します。まだ照合していないものは、「確認できない」ではなく**未照合**と表示します。

### 固定予定は、どう守っているのですか。

- 旅程の生成では、入力した固定予定を、AIが名前や時刻を変えても**入力どおり**に戻します。
- 画面では、固定した予定の「この予定だけ変更」は押せません。ただし、このボタンは、部分修正の入口がつながるPR #38以降の画面にだけ出ます（`main` の画面には、ありません）。
- データ契約では、固定された予定への修正を拒否します。
- 部分修正の候補は、対象の1地点だけを変えます（PR #28）。固定予定に間に合わない候補は、成立する案として出しません。
- 承認の前は、元の旅程を変えません。

### 学びは、何が保存されますか。

- 保存の対象は、**本人が承認した学びだけ**です。内容、種類（情報源との不一致／個人の好み）、適用範囲（全地域／同じ地域）、承認日時を持ちます。
- 編集した学びは、承認済みでも未承認に戻し、再承認を求めます。
- **`main` の画面は、保存先が未接続で、保存しません。** Firestoreへの保存と、利用者ごとの認可は、PR #44（レビュー中）です。
- 基盤モデルの再学習ではありません。

### Googleのデータは、保存していますか。

保存するのは **Place IDだけ**です。名称・住所・座標・営業時間・所要時間は、処理中にだけ使い、保存しません（`docs/MAPS_API_ADAPTERS.md`）。取得した内容を、AIモデルの学習や改善には使いません。なお、`main` では、Places・Routesを呼ぶAPIがなく、画面にGoogle Maps由来のデータは出ません。帰属表示と利用条件の対応表は、PR #40（レビュー中）です。

### 路線図は、地図ですか。

いいえ。訪問順を示す**模式図**で、実際の位置関係や縮尺は表していません。

### 公共交通は、扱えますか。

MVPでは、照会の対象外です。公共交通を使う案は、移動時間を「確認できない」とし、AIの推定で埋めません。Routes APIで、`TRANSIT` の実測が4回とも空だったことが理由です（`docs/API_CONNECTIVITY_FINDINGS.md`）。

### 臨時休業や渋滞は、考慮されますか。

いいえ。営業時間は通常営業時間だけで、渋滞や遅延は見ていません。そのため、「整合」を保証として扱いません。

### いま実際に動いているのは、どこまでですか。

README の「主な特徴と状態」を参照してください。`main` で動くのは、旅程の生成、路線図と固定予定の操作、学びの候補の編集・承認です。照合、部分修正、保存は、レビュー中のPRです。**デモでは、動いていない部分を、動いているように見せません。**

### 位置情報や個人情報は、集めていますか。

`main` のコードは、位置情報を取得しません。入力した旅行先・希望・固定予定・感想は、旅程の生成と学びの候補の作成のために、サーバーからGeminiへ送ります。APIキーはクライアントに渡しません。認証は匿名認証の基盤までで、一人一アカウントや身元は保証しません。

### 課金は、どう制御していますか。

課金を伴うAPIは、機能フラグで既定を無効にしています。認証・利用制限が入るまでは、意図した環境だけで有効にする運用です。利用制限そのものは、まだありません。
