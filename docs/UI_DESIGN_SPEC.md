## 2. 路線図とチケットの使い分け

- 観光や散策：標準の駅ノードで表示します。
- 食事やカフェ：路線図につながったフードチケット風カードを提案します。
- 固定した予定：元の表示種類を維持し、ロックを重ねます。
- **固定は予約・購入済みを意味しません。**
- 通常の徒歩・バス・地下鉄移動：駅と駅の間の移動区間に表示します。
- 新幹線・特急など時刻が重要な予定：乗車券風表現を検討します。
- チケットを全ての予定へ一律に適用しません。
- 予約券と誤認させるQRコードや購入済み表示は置きません。

### 公共交通の制約

- 現在のRoutesアダプターは徒歩と車に対応し、公共交通は扱いません。
- 公共交通の時刻・乗車時間を照合済みと表示しません。
- Geminiの提案した時刻や運賃を、確認済みの値として補完しません。
- #24で提案された交通用Stopと移動区間の区別を維持します。

## 3. UI表示と状態を独立させる

- 予定の種別：観光、食事、交通など。詳細な型はIssue #24で検討中です。
- 固定状態：`Stop.isFixed`による操作制限です。予約とは無関係です。
- 根拠：`consistent`、`conflicting`、`unverifiable`を分けます。
- 未照合：`evidence: []`で表し、`unverifiable`と混同しません。
- 制約：`not_checked`、`satisfied`、`violated`、`unknown`です。
- 承認：`pending`、`approved`、`rejected`です。
- 予約・購入：現行の共通契約には正本がありません。断定表示は禁止です。
- 現地完了：実績時刻と完了状態の契約は未定義です。
- 状態は色だけでなく、文言や記号でも区別します。
- 情報源、照合日時、対象日時と適用範囲を閲覧できるようにします。
- 「情報源と整合」は現実の正しさを保証する表現ではありません。

## 4. 基本の画面と操作

### A. 旅程生成・一覧

1. 行き先、日付、希望条件を入力して候補を生成します。
2. Geminiの結果は未承認の提案として表示します。
3. 路線図では順序、時刻、推定滞在時間、固定予定を区別します。
4. 必要な予定だけを選んで部分修正へ進みます。

### B. 変更候補の比較・本人承認

1. 変更するStopと理由を明示します。
2. 元の予定を保持したまま、候補と変更前後の差分を表示します。
3. 価格と移動時間は出典がある値と見積り、不明を区別します。
4. 変更前後の移動区間と後続の固定予定への影響を示します。
5. 根拠の照合と決定論的な制約検証を別の判断として扱います。
6. 実行不可能な候補を採用可能として表示しません。
7. 本人の明示的な承認前に元の旅程を書き換えません。
8. 通信失敗や候補なしでも元の旅程を保持します。
9. 候補A・B・Cの実行可能性を、候補ラベルで決めつけません。

### C. 現地対応・振り返り

- 現地のトラブルは、旅行前と同じ部分修正フローを再利用します。
- 模擬報告と本人による実際の報告を区別します。
- 学びは本人が編集・承認した場合だけ保存します。
- 次回旅程では承認した学びと反映先を明示します。
- 基盤モデルが再学習したとは表現しません。

## 5. チケットを切る操作（未確定）

- 食事の終了時刻はAIの推定と本人による実績を分けます。
- 操作名は「食事を終えた」などの明示的な文言を検討します。
- チケットを切る演出は入力手段の代替にしません。
- 誤操作時の取り消しと実績時刻の修正を検討します。
- 後続の時刻変更が必要なら、部分修正と承認を経由します。
- 固定予定を解除したり、承認なく時刻をずらしたりしません。
- 現在の`Stop`に実績時刻と完了状態はなく、別途契約が必要です。
- 既存のMVP必須機能をこの演出で置き換えません。

## 6. ビジュアルと実装のルール

- モバイル縦画面を優先し、390px前後で確認します。
- 標準駅、食事カード、ロック、状態表示、比較シートを再利用します。
- オレンジ、黒、オフホワイトは元のモックからの検討案です。
- 色、書体、余白、角丸、アニメーションは未確定です。
- 小画面でも重大な注意、固定予定、承認操作を隠しません。
- キーボード操作、フォーカス、コントラストを確認します。
- Maps Platform由来のデータには必要な帰属表示を行います。
- Googleの出典は視認可能に示し、帰属を飾りとして扱いません。
