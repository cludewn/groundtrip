# GroundTrip UIデザイン共有仕様

更新日：2026-11-07

**位置付け：MVPで採用するUI設計を共有する仕様書。** 路線図を主軸とした画面構成・色の役割・比較操作・ボトムシート・通知の方向性は採用済みとする。まだ開発していない機能や将来案は別に扱う。UI設計の採用は、API接続・永続保存まで実装完了したことを意味しない。

## 1. 目的と参照順序

GroundTripの核は **「AIの提案を、人間が根拠で選ぶ（Own the Why）」**。AIのミス探しを強いるのではなく、使いやすい部分修正と本人の判断を両立させる。

- プロダクト上の不変条件：`docs/PRODUCT_AND_ARCHITECTURE.md`
- UIでの利用者保護・操作の原則：`docs/UX_DESIGN_PRINCIPLES.md`
- 正式な型・API契約：`docs/DOMAIN_CONTRACTS.md`、Issue #24、各機能の最新PR
- この文書：**画面表現、操作の意味、採用案と残課題**を共有する。契約や合意済みIssueを上書きしない
- Figmaは視覚的な補助資料として使用する。採用済みのUI方針を本書へ記載するために、承認済みフレームの完成を待つ必要はない

### 採用済みの設計と未実装機能

- **採用するUI設計**：本書§2〜§5の画面表現と操作の方針。細かな数値や実装手段は、機能を損なわない範囲で調整できる
- **実装の進捗**：Issue・PRと実コードで確認する。本書の仕様採用をもって、未マージのコードが`main`で動作すると解釈しない
- **対象外・未決定**：§7の拡張機能。MVPのUI設計を未確定へ戻す理由にはしない

## 2. 旅程表示：路線図とチケット

**採用している基本構成：縦型路線図。** 予定を駅として時刻順につなぐ。路線図は訪問順の模式図であり、実際の縮尺・位置関係を表す地図ではない。

- 観光・散策など：通常の駅ノード
- 食事・カフェ：駅の順序とつながる**食事チケット型カード**。#20で採用した表示の方向を維持する
- 固定予定：元の予定種別・カード/駅の形を**変えずに**ロックと「固定予定」の表示を追加する。#20で修正済み
- 固定は「予約済み」「購入済み」ではない。「要予約」も予約完了の証拠ではない
- 徒歩・車などの移動：前後のStop間の移動区間として表示する。移動そのものが独立した予定（乗車・乗換など）なら`Stop.kind: 'transport'`を使用できる
- 新幹線・特急の**乗車券風表現は未決定**。契約にない予約・購入済み状態や実在するQRコード等を描かない
- すべての予定を一律にチケット化しない

### 種別と移動区間の契約（#24／PR #25）

**決定済み・PR #25はmainにマージ済み。**

- `Stop.kind?: 'sight' | 'meal' | 'transport' | 'other'` は任意。未指定は「予定」と表示し、観光と推測しない
- `kind`、`isFixed`、予約・購入状態は別の概念
- `TravelSegment` は`Trip`に含めない独立モデル。現在は永続保存しない
- `known`は照合日時と出典、`walk`／`drive`の移動時間を持つ。`unknown`は理由を持ち、未照会・API失敗・経路なし・未対応を区別する
- 公共交通は現在のRoutesアダプターでは未対応。`transit_unsupported`を利用者に説明し、AIの推測を照合済み所要時間にしない
- 価格契約は**#24で未決定**。架空の金額や推定値を検証済みの比較に流用しない
- #20の`RouteMeta`は当初のUI暫定値。共有モデルとの接続は各機能PRで段階的に整理する。契約と暫定値の混在を隠さない

## 3. 状態の意味を分離する

- **根拠の照合：** `consistent`／`conflicting`／`unverifiable`。情報源と整合／矛盾あり／確認できない。
- **まだ照合していない：** `evidence: []`は「未照合」。「確認できない」と混同しない。
- **制約検証：** `not_checked`／`satisfied`／`violated`／`unknown`。予定への影響を平易に説明し、裏付けを詳しく確認可能にする。
- **本人の判断：** `pending`／`approved`／`rejected`。候補／承認／却下。承認とサーバーへの適用・保存は別。
- **固定：** `Stop.isFixed`。ロックと「固定予定」。予約の有無は示さない。

**表示の原則：**

- 出典・照合日時・対象日時・説明を確認できるようにする。「情報源と整合」は、当日営業や現実の正しさを保証しない
- 施設の存在、営業時間、移動所要時間は**別の確認対象**。まとめて「全部確認済み」としない
- 制約の`satisfied`を「予定に収まる」と表示する場合は、**実際に検証した範囲**を説明する。所要時間が未取得なら「次の予定に間に合う」と断定しない
- `unknown`／`violated`／`not_checked`の候補は承認可能として出さない。未確認の理由を示す
- 候補なし、情報不足、API失敗、通信中断を区別し、元の旅程を維持する
- 色だけに頼らず、形の一貫したアイコン・文字ラベル・必要な説明を付ける

## 4. 画面・操作フロー

### A. 旅行前：生成と旅程一覧

1. 行き先・日付・希望条件から日帰りの旅程を生成する
2. 生成されたTripは提案段階であり、自動で本人承認・保存したことにしない
3. 一覧は予定時刻・滞在時間・移動区間・固定予定・重大な未確認事項を見つけやすくする
4. 予定を選んで詳細（根拠・時刻・価格がある場合の性質）を開き、変更可能な1地点から部分修正へ進む
5. 固定予定は変更対象にしない。固定の切り替えは本人の明示操作による。**#20の固定操作はローカルUIのみで、永続保存は#10の担当**

**生成前に「外せない予定」を入力する案**は利用者上の課題として残る。現在の生成フォームは`fixedStops: []`を送る。固定予定の事前入力は追加機能の検討対象であり、実装済みではない。

### B. 比較と本人承認（#9）

1. 修正するStopと理由、必要な条件を明示する。元のTripと固定予定は保持する
2. 未承認の候補を切り替え、**選択中の分岐を路線図に表示**する。元の経路との再合流点を理解できるようにする
3. 元の予定と候補の差分、前後の移動時間、後続の固定予定への影響を示す。比較できない値は「未確認」とする。**同じ移動手段・取得条件で比較できる場合にだけ**数値差を示す
4. 根拠（照合）・制約チェック・本人承認を別々に扱う。候補A/B/Cというラベルだけで適否を決めない
5. 実行不可能・未確認の案を確定可能と扱わず、利用者が承認するまで元Tripを変更しない
6. 失敗・候補なし・キャンセル・遅い応答によって元Tripや固定予定を壊さない
7. 実際の適用時はサーバーで所有者・Tripの版・変更前Stop・固定条件・移動時間を再検証する

**採用する比較画面：** 候補の切り替えを路線図の直前に配置し、選択中の分岐・元の経路・再合流先と、根拠や時間の差分を対応させて示す。利用者向けの文言を優先し、確認日時や詳細な検証内容は展開して参照できるようにする。

**実装上の依存：** #9の候補生成（PR #28）、比較UI、承認・適用API、#10の認可・保存はそれぞれ別の作業である。UIの実装では、共通スキーマによる候補数・移動区間・応答全体の検証と、元Trip・版・Stopとの対応チェックを維持する。未接続の承認・保存を成功したように表示しない。

### C. 旅行中・振り返り・次回

- 旅行中は**現在・次の予定、時間制約と再計画**を優先する。旅行前の全旅程表示とは情報の優先順位を変える
- 進行状態を表す場合は手動操作や予定時刻からの表示とし、GPSで実際の現在地を追跡しているかのように見せない
- 現地報告（実際／模擬）を区別し、旅行前と共通の部分修正フローを可能な限り利用する（#11）
- 体験と情報源の食い違いを区別し、本人が編集・承認した学びのみを保存し（#12）、次回反映先を説明する（#13）。基盤モデルの再学習とは呼ばない

## 5. 採用するビジュアルと操作

**MVPの画面では、次のデザインと操作の方針を採用する。** 色コード・アニメーション時間などの細部は、視認性や動作確認に基づいて調整できる。

- **青：比較中の未承認候補の分岐**、**グレー：元の経路や補助線**、**オレンジ：適用済み／旅行中の注目区間**を基本にする。緑は根拠の整合など別の意味で使い、候補を「採用済み」と誤認させない
- 路線図の枝分かれだけで変更を伝えず、変更対象・前後差分・候補名を明示する
- 食事チケット・標準駅・ロック・ステータスの部品を共通化する。フォントサイズ、文字のコントラスト、余白、ボタンの高さを統一する
- 「安い」「うまい」など取得できていない値によるランキングは実装しない。「費用を抑えたい」「食事を重視」などの希望入力とは分ける。価格契約は#24の未決事項
- スマホ幅（320px／390px）で横はみ出し、タップ範囲、主要CTAの到達、キーボード・フォーカス・読み上げを確認する。PC幅でも極端な拡大を避ける
- 操作の意味を示す**アニメーション**（詳細シート開閉、入力から比較、候補切替、読み込み・エラー）を使用する。目安はシート開220ms／閉180ms、候補切替200ms。状態を理解できることを優先し、操作を妨げる演出を増やさない
- `prefers-reduced-motion`を尊重し、動きを抑えても操作結果が分かるようにする
- **予定詳細のボトムシート**は、ハンドルの下ドラッグ・背景タップ・明示的な「閉じる」ボタン・Escで閉じられる操作を採用する。短いドラッグは元の位置へ復帰し、内部スクロールやボタン操作を妨げない。閉じた後のフォーカスを復帰させる
- **画面全体をGroundTripの明色テーマに統一**する。ページ背景もアプリの一部であり、Next.jsが用意する別画面ではない。OSのダーク設定によって、一部だけが暗い背景へ切り替わらないようにする。路線図全体の不要な外枠より、必要なカードや詳細シートの区別を優先する
- キャンセル・エラー・成功の通知は、周囲の背景と文字が同化しない十分なコントラスト、内容に応じた幅・余白・枠線、結果を表す文言を用いる。`role="status"`／`role="alert"`などの通知の意味も維持する
- 表示の変化を装飾だけにせず、誰が何を承認したか、何が変わったかを識別可能にする

## 6. Google Maps Platformの表示境界

- Places／Routes由来の情報をGoogleマップ以外の画面（路線図など）に表示する場合、適用される**Googleの帰属表示**を必要な位置に示す。詳細は`docs/API_CONNECTIVITY_FINDINGS.md` §5
- 路線図は訪問順の模式図とし、実際の地図・縮尺・位置関係を再現しない。非Googleの地図との併用禁止に抵触しないよう確認する
- Google由来のデータの保存範囲は#10と利用条件に従う。Place IDの扱いと施設詳細・移動時間の保存を混同しない
- 現在地を取得する機能を追加する場合は、収集内容を通知して必要な事前同意を得る。現状、GPS常時追跡はMVPの前提ではない
- デモの架空施設・時刻・価格・模擬照合結果には**モック表記**を付け、実データと混同させない
