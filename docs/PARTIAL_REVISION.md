# 部分修正（Issue #9）の候補生成と制約検証：責務の境界とAPI

Issue #9（1地点の部分修正）のうち、**代替候補の生成・照合・制約検証・未承認Revisionの返却**まで。
候補の比較UI、本人承認、旅程への適用は、別の担当（`Cludewn`）で、このドキュメントの範囲外。
#11（現地報告からの再計画）も、**同じ処理**を使う（`context`で、旅行前と現地報告を区別する）。

## 責務の分担

| 担当                         | 責務                                                                                                                                         |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 候補の生成・検証（この文書） | 代替候補（最大3件）をGeminiで作る → Placesで施設を特定・営業時間を確認 → Routesで前後の移動と固定予定への影響を検証 → 未承認のRevisionを返す |
| 比較UI・承認・適用           | 候補の比較表示、本人の承認、旅程への適用。**適用の直前に、サーバー側で認可・版・制約を再検証する**                                           |

候補の生成側は、**元のTripを更新しない**。保存もしない。返すのは、未承認（`pending`）のRevisionだけ。

## API：POST /api/trips/revise

共通契約（`src/domain/contracts.ts`）の`ReviseTripRequest`／`ReviseTripResponse`をそのまま使う。

- リクエスト：`{ trip, targetStopId, reason, context }`。`context`は`{ phase: 'planning' }`か、
  `{ phase: 'on_site', report: { kind: 'actual' | 'simulated', description } }`。
  対象は、存在し、固定されていない予定だけ（契約で検証）。
- 成功：HTTP 200、`{ status: 'proposed', revisions }`。1〜3件。**すべて`pending`**で、同じ旅程・版・対象。
- 失敗（元の旅程は維持される）：`no_candidates`／`insufficient_information`は422、`external_service_error`は502。
  API層のエラーは、旅程生成APIと同じ（400／413／415／500／503）。
- **機能フラグ`TRIP_REVISION_ENABLED=true`のときだけ受け付ける**（既定は無効・503）。GeminiとMapsを呼ぶため。

## 処理の流れと判断

1. **候補の生成（Gemini、1回）**：対象1件だけの代替候補（名称と、短い理由）を最大3件。
   開始時刻・滞在時間・種別は、**変えない**（他の予定の時刻も、ずらさない）。AIは、Place ID・根拠・承認状態を決めない。
2. **候補の整理**：元の名称・他の予定の名称・重複を除く。
3. **照合（Places）**：候補を入れた旅程を、`verifyTrip`（#7）で照合する。施設を特定できない候補
   （候補なし・名称不一致・複数で絞れない）は、**実在を確認できないため、候補にしない**。
4. **制約の検証（Routes・営業時間）**：候補ごとに、**前の予定→候補**と**候補→次の予定**の、両方の移動を確認する
   （徒歩で間に合えば徒歩、間に合わなければ車）。次の予定が固定予定でも、他の予定の時刻は動かさないため、
   「候補の終了＋移動時間 ≦ 次の予定の開始」で、固定予定への到達も判定できる。
5. **制約検証の結果（`constraintCheck`）**：
   | 状態        | 条件                                                                                                          |
   | ----------- | ------------------------------------------------------------------------------------------------------------- |
   | `violated`  | 営業時間が矛盾する、または、前後どちらかの移動が間に合わない → **候補にしない（成立する候補として扱わない）** |
   | `satisfied` | 営業時間と、前後の移動が、すべて「情報源と整合」                                                              |
   | `unknown`   | 上記以外（営業時間・移動の、どちらかを確認できない）。**候補として返すが、承認はできない**（契約どおり）      |
6. **Revisionの組み立て**：`diff.before`は入力の予定、`diff.after`は候補（Place IDは、名称が一致した施設だけ）。
   根拠（`evidence`）は、`after`に付ける：施設の存在・営業時間・前の予定からの移動・**次の予定への移動**（`travel_time`）。
   `impactSummary`は、決定論的に組み立てる（AIの文章ではない）。

## 失敗の区別

| 状況                                               | 応答                                                    |
| -------------------------------------------------- | ------------------------------------------------------- |
| Geminiの失敗                                       | `external_service_error`                                |
| Mapsの呼び出しが、すべて失敗                       | `external_service_error`（根拠を捏造しない）            |
| AIが作れないと申告                                 | その状態（`no_candidates`／`insufficient_information`） |
| 候補が、すべて除外された（特定できない・制約違反） | `no_candidates`（理由を、利用者向けに説明）             |

## 適用時の再検証のための、再利用できる関数

承認・適用の処理（比較UIの担当）が、**適用の直前**に、サーバー側で制約を再検証できるよう、
`checkRevisionConstraints`（候補を旅程へ入れた状態で、営業時間・前後の移動を再検証し、`ConstraintCheck`を返す）を公開する。
クライアントが返した`constraintCheck`や`evidence`は、承認の根拠として信用しない。

## 未決定（Issue #24と合わせて決める）

- **変更前後の移動区間の比較**を、APIの応答でどう返すか。案：`proposed`に、任意の`comparisons`
  （`revisionId`ごとに、前後の`TravelSegment`）を足す。`tripId`・`baseTripVersion`・`targetStopId`・候補との対応を維持し、
  一時的な比較データとして返す（保存しない）。現在の応答は、`evidence`と`impactSummary`の説明文で、移動の可否を示す。
- 候補の時刻・滞在時間を変える修正（対象外の予定の時刻変更を含む）は、今回は扱わない。
