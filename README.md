# GroundTrip

> AIが作った日帰り旅行の提案を、根拠を見ながら自分で選べるアプリ。「AIの提案を、人間が根拠で選ぶ（Own the Why）」。

GroundTripは、観光とAIリテラシーを組み合わせた旅行アプリです（GDG DevFest Japan Hackathon 2026 向けの開発）。
Geminiが旅程を**提案**し、地図サービスの情報による**照合**、時刻や固定予定の**制約チェック**を経て、最後は**本人が承認**します。
この4つを混ぜません。

## 解決したい課題

- AIが作る旅程は、もっともらしく見えますが、**施設が実在するか、その日に営業しているか、移動が間に合うか**といった根拠が見えません。
- 旅行中は、閉店や遅れで予定が崩れます。AIの提案をそのまま信じていると、固定した予約まで巻き込んで作り直されるおそれがあります。
- 旅行の後に残るのは、感想だけです。次の旅行に活かす手がかりが、本人の判断を通さずにAIの中へ入ってしまうのも避けたい点です。

GroundTripは、旅程の**一部だけ**を便利に直す操作の中で、事実・未確認・制約・選んだ理由を確認できるようにします。AIのミス探しを、利用者に強いません。

### 1. 旅程の生成

旅行先・日付・希望・固定予定を入力すると、Gemini（Vertex AI）が日帰り（1地域・3〜4地点）の旅程を**提案**します。

- 実装済み（main）：旅程の生成API（#17）、旅程の作成フォーム（固定予定の入力つき、#18・#37）。
- 生成された地点は、施設を特定していない**未照合**の状態で表示します。Geminiの出力は、施設の実在・営業・移動時間の証拠として扱いません。

### 2. 根拠の照合

提案された予定を、Places・Routesの情報と突き合わせ、**情報源と整合／矛盾あり／確認できない**の3状態で示します。

- 実装済み（main）：Places・Routesのアダプター（#21）、根拠と移動区間のデータ契約（#15・#25）、根拠の3状態を表示する部品（路線図、#20）。ただし、アダプターを呼び出すAPIは `main` にありません。
- レビュー中（未マージ）：施設の同定・営業時間・移動の照合ロジックと `POST /api/trips/verify`（PR #27）。
- 未着手：生成した旅程の画面への、照合結果の接続（PR #27 の本文で「別のPR」とされています）。

### 3. 1地点の部分修正と、本人の承認

変えたい予定を**1つ**だけ選び、代替候補を比べて、本人が採否を決めます。固定予定と、承認前の旅程は変わりません。

- 実装済み（main）：縦型の路線図、予定の詳細シート、固定予定の切り替え（#20）。
- レビュー中（未マージ）：代替候補の生成と制約検証、変更前後の移動区間の比較（PR #28。PR #27 の上に積んだPR）。候補の比較画面と承認の操作（PR #38）。
- 未着手：承認した修正の、サーバーでの適用と保存（PR #38・#44 の本文で後続作業とされています）。

### 4. 現地の報告からの再計画

旅行中の閉店や遅れを報告し、旅行前と同じ部分修正の流れで直します。

- 実装済み（main）：現地の状況の報告フォーム（#41）。ただし、どの画面にも組み込まれていません。
- レビュー中（未マージ）：旅行中の「いまの予定・次の予定」の表示（PR #42）、内部の状態を平易な言葉に変換するロジック（PR #43）。
- 未着手：報告フォームから部分修正への接続。

### 5. 振り返りと、本人が承認した学び

旅行後の感想から、Geminiが学びの候補（1〜3件）を作ります。本人が編集し、承認したものだけを残します。

- 実装済み（main）：学びの候補の作成API（#22）、候補の編集・承認・却下の画面と、承認済みの学びの保存の接続口（#26・#39）。画面は `/reflection` で、旅程はサンプル（架空）です。
- レビュー中（未マージ）：Firestoreへの保存と、利用者ごとの認可（PR #44）。
- 未着手：実際の保存先への接続。`main` の画面は、保存先が未接続のため、承認した内容を保存しません（画面にもそう表示されます）。

### 6. 次回の旅行への反映

承認済みの学びを、次の旅程の生成に使い、どこに反映したかを示します。

- 実装済み（main）：生成APIが承認済みの学びを受け取り、反映先を記録できるデータ契約と生成処理（#15・#17）。
- 未着手：画面からの利用。旅程の作成フォームは、学びを常に空で送ります。保存した学びを取り出して生成に渡す処理もありません。

## 設計の原則

詳細は [`docs/PRODUCT_AND_ARCHITECTURE.md`](docs/PRODUCT_AND_ARCHITECTURE.md) と [`docs/UX_DESIGN_PRINCIPLES.md`](docs/UX_DESIGN_PRINCIPLES.md) にあります。

- **4つの分離**：AIの**提案**、外部情報による**照合**、決定論的な**制約チェック**、**本人の承認**を、別の責務にします。Geminiの文章を、正しさの証拠にしません。
- **「情報源と整合」は、現実の正しさの保証ではありません**。整合は、取得した時点の情報源と合っていたことを表します。臨時休業や当日の混雑は、保証しません。
- **固定予定の保護**：本人が固定した予定は、修正の対象にしません。承認の前は、元の旅程を変えません。
- **失敗の区別**：「候補なし」「情報不足」「外部サービスの失敗」を区別します。失敗したときに、AIの推測で根拠を埋めません。
- **学びは本人が承認したものだけ**：編集した学びは、承認前に戻して再承認を求めます。これは、基盤モデルの再学習ではありません。
- **模擬は模擬と示す**：デモ用の想定や架空のデータを、実測や実際の報告と混ぜません。

### プロダクトの中のAI（Gemini）の使いどころ

- **旅程の提案**（`main`）：条件から日帰り旅程を作ります。出力はZodで検証し、固定予定は入力どおりに置き換えます。施設は未同定・未照合のまま返します。
- **学びの候補の作成**（`main`）：感想と、承認済みで模擬でない変更から、候補を1〜3件作ります。候補はすべて未承認で、本人が承認したものだけを残します。
- **部分修正の代替候補**（PR #28、レビュー中）：選んだ1地点だけの代替を、最大3件作ります。成立するかは、Places・Routesと時刻の制約チェックで確かめます。
- **Geminiがしないこと**：根拠の証拠になる、承認する、施設の実在や営業を判断する。基盤モデルの再学習もしません。

Geminiを選んだ理由と、各APIを選んだ理由の文面は、`docs/` に記載がありません。提出文書に書く前に、チームで確認してください（`docs/API_CONNECTIVITY_FINDINGS.md` には、`responseSchema` で検証用のJSONを生成できたという実測があります）。

## 制限事項

- **MVPの範囲**：日帰り・1地域・3〜4地点・1地点の部分修正です。複数日の最適化、GPSの常時追跡、個別のAI学習は、対象外です。旅程のタイムゾーンは、フォームでは日本時間に固定しています。
- **照合で分からないこと**：臨時休業・特別営業・渋滞・遅延・当日の混雑は、考慮しません。営業時間は通常営業時間だけです。公共交通は照会せず、「確認できない」として扱います。
- **路線図は模式図**です。訪問順を示すもので、実際の地図ではありません。
- **一部はデモ用の模擬データ**です。`/demo` と `/reflection` の旅程、およびサンプルの根拠は、架空のものです。実在する施設の情報ではありません。
- **課金を伴うAPIは、機能フラグで停止しています**。旅程の生成と学びの候補の作成は、既定で無効です（レビュー中の照合・部分修正のAPIも、同じ方針です）。認証・利用制限（App Checkを含む）が入るまでは、意図した環境だけで有効にしてください。
- **認証は基盤だけ**です。匿名認証は、一人一アカウントや身元を保証しません。認証状態を失うと、保存データに戻れない場合があります。
- **生成された旅程は提案**です。承認・保存・確定ではありません。AIの内容は、施設の実在・営業・価格を保証しません。

## 外部サービスの扱い

- **Google Maps Platform（Places・Routes）**：保存するのは **Place ID だけ**です。名称・住所・座標・営業時間・所要時間は、処理中にだけ使い、保存しません。取得した内容は、AIモデルの学習・改善に使いません。根拠は [`docs/MAPS_API_ADAPTERS.md`](docs/MAPS_API_ADAPTERS.md) と [`docs/API_CONNECTIVITY_FINDINGS.md`](docs/API_CONNECTIVITY_FINDINGS.md) §5 にあります。
- **帰属表示と利用条件**：Googleの帰属表示、アプリ側の利用規約・プライバシーポリシーの要件と、実装の対応表は `docs/GOOGLE_MAPS_COMPLIANCE.md` にまとめています。**このファイルと帰属表示の部品は、PR #40（レビュー中、未マージ）で、まだ `main` にありません。** 現時点の `main` は、画面にGoogle Maps由来のデータを表示しません（アダプターを呼ぶAPIがないため）。照合を画面に接続するときに、帰属表示を組み込む必要があります。
- **Gemini（Vertex AI）**：旅行先・日付・希望・固定予定・感想などの入力が、サーバーからGeminiへ送られます。APIキーはクライアントに渡さず、サーバー側のADCで認証します。
- **Firebase**：`main` では、匿名認証の基盤とEmulator用の設定までです。利用者のデータの保存は、PR #44（レビュー中）です。
- **秘密情報**：環境変数の変数名は [`.env.example`](.env.example) にあります。実際の値は、コミットしません。

## 開発環境

- Node.js 24.15以上の24系
- pnpm（バージョンは`package.json`に準拠）

### セットアップ

依存関係をインストールします。

    pnpm install --frozen-lockfile

開発サーバーを起動します。

    pnpm dev

ブラウザで http://localhost:3000 を開いてください。

### 検証

以下のコマンドを実行します。

    pnpm format:check
    pnpm lint
    pnpm typecheck
    pnpm test
    pnpm build

共通データモデル・入出力契約の利用方法と未決定事項は
